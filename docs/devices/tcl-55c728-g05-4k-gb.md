# TCL 55C728 (`G05_4K_GB`): setupwraith stayed off across a reboot

Report from [#734](https://github.com/Gathin23/cleanyourtv/issues/734): one owner, one same-day
session, done with his own ADB scripts and a small custom Java launcher instead of
`launcher/build-and-install.sh`. He applied the packages below and rebooted, but has not lived with
them for days and did not exercise an undo. [CONTRIBUTING](../../CONTRIBUTING.md) asks for a few days
of use before a list goes into `examples/`, so this is a note, not a list: read it next to
[`examples/tcl-g05-google-tv/`](../../examples/tcl-g05-google-tv/debloat.txt), which is the same board
on different firmware.

## Identify the firmware, not the retail name

| Field | Reported value |
|---|---|
| Retail name | TCL 55C728 ("Smart TV Pro"), owner-supplied |
| `ro.product.name` | `G05_4K_GB` |
| `ro.product.device` | `G05` |
| Android | Google TV on Android 11, SDK 30 |
| Build fingerprint | `TCL/G05_4K_GB/G05:11/AR2101/AR28` |
| RAM | 2.7 GB |
| SoC | MediaTek (`ro.hardware` not recorded, model not named in the report) |

The US list in `examples/tcl-g05-google-tv/` is the same `G05` board sold as `G05_4K_US`, on the same
`AR2101` build ID with incremental `AR68`. Matching on "55C728" or on "G05" alone therefore says
nothing about the two questions below; match `ro.build.fingerprint` first.

## The reboot question: this build keeps setupwraith disabled

The US list reported the only G05 unit so far where disabling
`com.google.android.tungsten.setupwraith` did not stick: that `AR68` set had it back in charge after a
reboot. Two `G05_4K_GB` reports say otherwise:

| Set | Product | Build | setupwraith disable across a reboot |
|---|---|---|---|
| [`tcl-65c735/`](../../examples/tcl-65c735/debloat.txt) (France) | `G05_4K_GB` | `AR2101` | stayed off |
| this 55C728 (GB) | `G05_4K_GB` | `AR2101` / `AR28` | stayed off |
| [`tcl-g05-google-tv/`](../../examples/tcl-g05-google-tv/debloat.txt) (US) | `G05_4K_US` | `AR2101` / `AR68` | came back |

So the `AR68` unit is the exception among the three G05 reports, not the rule, and it is the build
ID (`AR2101`) that is shared by all of them - the incremental (`AR28`/`AR68`) is what actually
differs. Nobody here can say which change in `AR68` brings the recovery activity back, so check the
fingerprint on your own set and test one reboot before promising the handover to anyone.

What does carry over from the US report to this one: with only `launcherx` disabled, HOME went to
`com.google.android.tungsten.setupwraith/.RecoveryActivity` (priority 1) instead of the launcher.
Disabling the package, not just the component, is what moved Home; the shell still cannot change the
component's state on its own.

## Check the Wi-Fi creator before disabling setupwraith

On the Wi-Fi units of this family the network saved during first setup belongs to setupwraith, and
disabling it deletes the network (`tcl-g03-google-tv` and `tcl-55p8ls` both had to forget and
re-join first). This set is on Ethernet, and both checks came back empty:

```sh
dumpsys wifi | grep -o 'cname=[^ ]*'     # no output
cmd wifi list-networks                   # "No networks"
```

so disabling setupwraith cost nothing here. That is an answer for an Ethernet set only - the owner
did not test Wi-Fi at all, and Ethernet surviving does not prove the Wi-Fi credentials were never
setupwraith's.

## Home handover as it was done

HOME candidates before the handover, from `cmd package query-activities`:

- `com.google.android.apps.tv.launcherx/.home.HomeActivity`, priority 2
- `com.google.android.tungsten.setupwraith/.RecoveryActivity`, priority 1
- `com.android.tv.settings/.system.FallbackHome`, the last resort

After `pm disable-user --user 0 com.google.android.tungsten.setupwraith`,
`cmd package set-home-activity` to the owner's own launcher, and a reboot,
`dumpsys activity activities | grep mFocusedApp` still named that launcher and
`pm list packages -d` still listed every package he had disabled. Nothing was re-enabled at boot.

This was **not** the reference launcher: `launcher/build-and-install.sh` was never run, so its
preflight, its rollback and the b64push path are all still unverified on this firmware, exactly as
the US list's header says. Only the firmware behaviour carries over.

## Remote keys: what a launcherx-free set loses

Key events as they reached an accessibility key filter on this unit:

| Button | Keycode | Scancode |
|---|---|---|
| Netflix | 4062 | 566 |
| Prime Video | 4099 | 752 |
| Input | 178 (`KEYCODE_TV_INPUT`) | 471 |
| gear / settings | 4077 | 561 |

These match the `tcl-55c725` notes. With `launcherx` gone, all four did nothing until they were
remapped: TCL's window manager turns the Netflix and Prime Video keys into broadcasts that only the
stock launcher receives (the `tcl-65c735` header describes the same mechanism), so an accessibility
service has to catch the keycode and start the app itself. The Input key is the one worth keeping
mapped, because `com.android.tv.action.VIEW_INPUTS` opens `com.tcl.suspension`'s source overlay - it
is why this owner kept `com.tcl.suspension` enabled, the opposite of the US list, which disables it
and uses the launcher's own Inputs menu instead.

## Inputs and HDMI

Sources reported by the TV input framework:

- tuner: `com.tcl.tvinput/.TDTVInputService/HW1413742848`
- HDMI 1-4: `com.tcl.tvinput/.passthroughinput.TvPassThroughService/HW1413744128`, `.../HW1413744384`,
  `.../HW1413744640`, `.../HW1413745664`
- AV: `com.tcl.tvinput/.passthroughinput.TvPassThroughService/HW1413743104`

`ACTION_VIEW` on the HDMI passthrough URI resolves to `com.tcl.tv/.TVActivity` and switched to HDMI 1
on screen, with `com.tcl.tv` and `com.tcl.tvinput` both enabled. Screenshots of an HDMI input still
came back 0 bytes, which is the known capture limit rather than a fault of this set.

## What was not tested

- `launcher/build-and-install.sh`, its rollback and the b64push transfer: the launcher installed here
  was the owner's own, so nothing about the reference APK is confirmed on `AR28`.
- Undo. No `pm default-state` / `pm enable` run was recorded, so the original enablement states of
  these 23 packages are unknown; record them before you copy this, because most were `default` on the
  comparable sets, not `enabled`.
- Days of use. Everything here is same-day, and the report does not cover standby/wake, casting,
  Bluetooth pairing, firmware updates, or what the TV does after a second reboot.
- Wi-Fi, since the set was on Ethernet throughout.

## Second unit: TCL 65C835, Italy, Wi-Fi

A second owner ran this repo's tools on a TCL 65C835 with the same fingerprint,
`TCL/G05_4K_GB/G05:11/AR2101/AR28` (MediaTek `mt5889`, 2.7 GB), over one evening with several reboots. It is a
note for the same reason as the one above: hours of use, not days.

- **Wi-Fi, and setupwraith did not own it.** The set was on Wi-Fi throughout, and the saved network belonged to
  `android.uid.system:1000` (`dumpsys wifi | grep -o 'cname=[^ ]*'`), so `tools/disable.sh` disabled setupwraith
  with no forget and re-join, and the TV stayed on Wi-Fi. That is one Wi-Fi answer for this build, from a set
  whose network had been joined in Settings; a network saved during first setup can still belong to setupwraith.
- **The reference launcher, on `AR28`.** `launcher/build-and-install.sh` pushed the APK with b64push (md5
  matched) and installed it. Its first run rolled itself back as designed: with `launcherx` disabled, Home went to
  `com.google.android.tungsten.setupwraith/.RecoveryActivity`, and the script put `launcherx` back. With
  setupwraith disabled first, the second run moved Home to `com.gathin.tvhome/.MainActivity`, and Home and every
  disabled package held across the reboots.
- **Remote.** The gear sent `4077` as above and did nothing until `HomeKeyService` handled it
  (`settings_key_keycodes` `4077`, `HOME_KEY_SERVICE=1`). The Input key worked with only `HomeKeyService` bound,
  and holding Volume+ still repeated with it bound, on the real remote.
- **26 packages disabled**, all through `tools/disable.sh` in batches with a screenshot of Home between them:
  `com.tcl.ttvs`, `com.tcl.logkit`, `com.google.android.feedback`, `com.tcl.waterfall.overseas`,
  `com.tcl.dashboard`, `com.tcl.tv.tclhome_passive`, `com.tcl.channelplus`,
  `android.autoinstalls.config.google.gtvpai`, `com.google.android.videos`, `com.tcl.hearaid`,
  `com.google.android.marvin.talkback`, `com.google.android.syncadapters.calendar`, `com.tcl.ocean.instructions`,
  `com.tcl.browser`, `com.tcl.smartalexa`, `com.android.printspooler`, `com.tcl.android.webview`,
  `com.google.android.apps.tv.dreamx`, `com.google.android.apps.nbu.smartconnect.tv`, `com.android.wallpaperbackup`,
  `com.android.sharedstoragebackup`, `com.android.backupconfirm`, `com.android.hotspot2.osulogin`,
  `com.android.htmlviewer`, `com.google.android.apps.tv.launcherx` and `com.google.android.tungsten.setupwraith`.
  `com.tcl.ttvs` holds the system updater on this build, so this set gets no OTA updates until it is re-enabled;
  that was the owner's choice. Kept by choice: the Assistant, Chromecast, Miracast and T-Cast, AirPlay,
  `com.tcl.gamebar`, `com.tcl.ui_mediaCenter`, and `com.tcl.suspension` for the Input key.
- **17 packages were already gone before the cleanup.** At the start the set had 145 packages and 128 installed
  for user 0: `com.netflix.ninja`, `com.tcl.usercenter`, `com.tcl.partnercustomizer`, `com.tcl.messagebox`,
  `com.tcl.guard`, `com.tcl.gallery`, `com.tcl.keyhelp`, `com.tcl.initsetup` and
  `com.tcl.inputmethod.international` among them, removed for this user by whatever had been used on the set
  before. The list named 13 of them; `tools/disable.sh` recorded those as `absent` before disabling anything, and
  `tools/check.py` afterwards lists them as "not installed any more". That is the state the set started in, not a
  disable that came undone, and `tools/restore.sh` rightly leaves them alone. The set worked without `keyhelp`,
  `initsetup` and the TCL keyboard: remote, Input, HDMI, Wi-Fi, and typing with Google's keyboard.
- **Not tested here either:** days of use, standby and wake, casting, switching inputs from the launcher's Inputs
  menu, and `tools/restore.sh` end to end.

## Before you apply anything here

Verify the fingerprint (`tools/tv.py --probe`), re-run the two Home queries rather than trusting the
setter's `Success`, and record the original package states. Network ADB is temporary maintenance
access: turn debugging back off when you are done and check that port 5555 is closed.
