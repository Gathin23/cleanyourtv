# QUIRKS ON THIS FIRMWARE, in the order they will bite you:
#
# 1. pm disable-user persists to /data/system/users/0/package-restrictions.xml with a delay
#    (~10 s on AOSP). If you run disable.sh and power-cycle the TV straight away, the changes
#    are silently lost: packages come back as enabled=0 (DEFAULT). Wait, or run
#    `pm list packages -d` and confirm your packages are listed before pulling the plug.
# 2. `adb reboot` over TCP hangs holding the dropped connection. Kill the adb server right
#    after sending it and wait on port 5555 coming back instead of on the adb command.
# 3. The Android 11 shell cannot disable individual components of another app
#    ("SecurityException: Shell cannot change component state") and cannot `pm hide`
#    ("Neither user 2000 nor current process has android.permission.MANAGE_USERS"). So if a
#    package refuses to stay disabled, the shell has no second lever. `pm suspend` does work
#    and survives a reboot, but it does not stop services: an app that starts itself from its
#    own boot receiver keeps running with suspended=true.
# 4. com.google.android.apps.mediashell (Chromecast built-in) could NOT be kept disabled on this
#    firmware and is deliberately absent from the list below. It returns to enabled=1 about 35 s
#    after every boot, reproducibly. pm disable-user, pm suspend, per-component disable and
#    pm hide were all tried; the first is undone, the second does not stop it, the last two are
#    refused by the platform. Left enabled, at a cost of about 37 MB.
# 5. A DISABLED PACKAGE CAN LEAVE A PERSISTENT PROCESS RETRYING FOREVER, AND pidof WILL NOT
#    SHOW IT. org.droidtv.xtv is the persistent TV engine and has five outbound service
#    bindings. Two of them, eum and aurora, were on the first version of this list, and
#    BOTH leave xtv in a permanent retry loop when disabled. Neither is in the list above now;
#    both are in the DO NOT DISABLE block below.
#
#    org.droidtv.eum -- bound via CONTEXTUALHELP. About five retries per second, logged as
#      xtvContextInterface ... connectCotextService - Service failed to connec i is null
#    51 of them in 10 seconds of an idle TV. This one also BREAKS A VISIBLE FUNCTION, and not
#    the one you would guess: the Philips sources drawer opens and vanishes within a second,
#    so HDMI inputs stop being reachable from the remote's SOURCES key. SourcesService logged
#    a correct, complete source list every time and the drawer still died.
#
#    org.droidtv.aurora -- about five retries per second too, logged as
#      xtvService: xtvService handleConnectAurora
#    at a steady 201 ms interval, 59 in 30 seconds of an idle TV. This one breaks nothing
#    visible and costs little: xtv sits at 0.2% of one core while doing it. It is log noise
#    plus a retry that can never succeed. Re-enabling it is free in practice -- aurora's
#    process does not start at idle even when the package is enabled, so xtv only needed the
#    package to be resolvable.
#
#    `pm enable` on either took its counter to zero immediately, with no reboot.
#
#    THE METHOD, which is the transferable part: a live PID proves the process exists, not
#    that it is healthy. xtv held the same PID through all eleven batches while both loops
#    ran. And do not grep for a string you already know -- that is how I missed the second
#    loop for a day after fixing the first. Clear the log, wait 30 seconds on an idle TV,
#    then group EVERYTHING by frequency and look at what repeats:
#      adb shell logcat -c; sleep 30; adb shell logcat -d > idle.txt
#      # then collapse digits and count: anything repeating several times a second is a loop
#    On this set that takes an idle log from 130 lines per 30 s down to 50, and the 50 that
#    remain are the firmware's own heartbeats.
# 6. The replacement launcher takes over on its own. Projectivy declares
#    android.intent.category.HOME, so the moment com.google.android.tvlauncher is disabled the
#    system resolves HOME to it — immediately, without a reboot and without enabling any
#    accessibility service. Check with
#    `cmd package resolve-activity --brief -a android.intent.action.MAIN -c android.intent.category.HOME`
#    BEFORE disabling the stock launcher, and make sure your replacement is listed by
#    `cmd package query-activities` for that intent. If it is not, you will be left without a
#    home screen (see issue #90).
#

# Stock launcher and its content engine, replaced by launcher/ (or Projectivy).
# ORDER MATTERS: disable the launcher FIRST. com.google.android.tvlauncher holds a stable
# ContentProvider reference on tvrecommendations/.NotificationContentProvider, and
# ActivityManagerService kills a client holding a stable ref when the provider's process dies —
# so disabling tvrecommendations first force-stops the live 190 MB launcher process.
# tvrecommendations is also the only resolver for the system notification panel
# (OPEN_NOTIFICATIONS_PANEL and friends), so that panel is gone device-wide, not just from the
# stock home screen. That is a conscious trade, not a side effect.
# com.google.android.tvlauncher   # launcher/build-and-install.sh disables the stock launcher itself, after Home has moved # 190 MB resident, the single heaviest process on this TV
com.google.android.tvrecommendations      # "Android TV Core Services" despite the name: recommendation rows, channels, notification panel
